## 2026-08-05 — Typo-tolerant fuzzy search, extended relevance scoring

User asked to improve search so typo'd/misspelled queries still find items. The existing match logic (`normalizeSearchText`/`tokenizeSearchText`, from the 2026-07-10 "Weetbix" fix) was punctuation/spacing-tolerant but still exact-substring only — a genuine misspelling ("weibix", "bananna") returned nothing.

- Added a Levenshtein-distance-based fuzzy fallback (`levenshteinDistance`, `typoBudgetForLength`, `isFuzzyWordMatch`, `isFuzzyProductMatch`) layered underneath the existing exact/substring matching, not replacing it — only evaluated when the free substring checks all fail, so a correctly spelled search pays no extra cost.
- Typo budget scales with word length (0 edits for <=3 chars, 1 for 4–5, 2 for 6–9, 3 for 10+), keyed off the length of the word as typed — an early version keyed it off `Math.max(typed, candidate)` length instead, which let short queries like "tea" wrongly fuzzy-match longer unrelated words ("teal", "team") just because the candidate was longer; caught by an independent second-pass review and fixed.
- New `tokenizeForFuzzy` (splits on whitespace only, keeps hyphenated names like "Weet-Bix" glued together as "weetbix") sits alongside the existing `tokenizeSearchText` (splits on all punctuation) — needed so an un-hyphenated typo'd query ("weibix") can still get close enough to a hyphenated real product name.
- `getSearchRelevance` extended from 4 tiers to 6: whole-word category (6) > whole-word name (5) > whole-word brand (4) > real substring match (3) > fuzzy/typo-only match (2) > fallback (1) — fuzzy always ranks below a genuine (even non-whole-word) substring hit.
- Wired into both search entry points: the main `SearchTab` results filter and `HistoryTab`'s check-history search.
- Product name/brand/category tokens are cached per product in a `WeakMap` to avoid re-tokenizing the same ~12.7k-item catalogue from scratch on every fuzzy fallback scan.

**Peer review:** compiled `#app-source` with the project's pinned Babel config — clean. Since this is a pure logic change (no rendered-screen/DOM changes), verification was a standalone Node unit-test harness against the extracted helpers rather than the usual jsdom render harness: confirmed target typos match (weibix→weetbix, bananna→banana, yoghurt→yogurt, milkk→milk, choclate→chocolate), unrelated short words stay rejected (tea/pea, jam/ham), relevance tiers score correctly, multi-word typo'd queries work, and a 13,000-product synthetic perf check stayed under ~70ms worst case. A fresh, independent second-agent review (given only the diff, no prior context) caught the short-word budget bug described above and flagged the per-product re-tokenization as avoidable overhead, which prompted the `WeakMap` cache. Known, deliberately-left limitation: same-length 4–5 character word collisions (e.g. "soap"/"soup", "beef"/"beer") remain possible at the 1-edit budget for that length tier — tightening it further would break the flagship "weibix"→"weetbix" case, so it's documented rather than changed.

Full write-up in `project.md` (2026-08-05, "Typo-tolerant fuzzy search added, relevance scoring extended" entry).

## 2026-08-04 — Restyled to the "Dodgy Deal · Mobile UI Kit" Claude Design system (Paper/Ink/Fair Green/Dodgy Yellow/Alert Red/Stone, Manrope + Inter)

User built a new design system as a Claude Design artifact (`claude.ai/code/artifact/ef788771-f9c7-43b2-aa6f-69a5c1f443b3`, "Dodgy Deal brand guide") and asked for the prototype restyled to match. Pure visual/styling pass — no component structure, props, or behavioural logic changed.

**Getting the design system content was the hard part.** The artifact renders inside a cross-origin `<iframe sandbox>` (`*.frame.claudeusercontent.com`) that the browser extension's synthetic click/scroll/keyboard input could not reach at all — confirmed by hit-testing (`elementFromPoint` at the scale-corrected coordinates landed exactly on the `<iframe>` element in the parent DOM every time, but the event never made it to the nav links or scroll position inside), not just a coordinate-math bug. Direct `fetch()` of the internal `GET /api/frame/versions/{id}` endpoint (the exact URL the page itself calls successfully) returned 404 even with `credentials:'include'` and the app's own cookies — some required Anthropic-internal header wasn't reproducible from outside the app's own request pipeline. The Vercel `import-claude-design-from-url` tool successfully imported and deployed a mirror, but the deployment sat behind Vercel Authentication with no accessible team/project to disable it from. **What worked:** the artifact's content, once loaded, was static HTML already painted into the iframe — resizing the iframe *element* itself (`style.height = '20000px'` from the parent, which really does resize the nested browsing context's own viewport, not just its CSS box) caused everything already mounted to render without needing the iframe's own internal scroll at all; a short `setTimeout` wait let the reference site's own scroll-triggered fade-in animations catch up. Walked the full page in ~750px increments (page-owned `window.scrollTo`, since the *parent* window's own scroll works fine — only the iframe's internal scroll was blocked) and screenshotted every section. For exact hex values (not just eyeballing), used the `computer` tool's `zoom`+`save_to_disk` on the color-swatch region and sampled real pixel RGB via a small Python/Pillow script in the sandbox rather than reading them by eye off a JPEG.

**Design tokens extracted** (Foundations → Quick reference, sampled and averaged over multiple points per swatch to reduce JPEG-compression noise):
- Colors: **Paper** `#faf8f4` (page bg), **Ink** `#171710` (primary text/buttons, near-black), **Fair Green** `#6ccb85` (positive/genuine), **Dodgy Yellow** `#e2c560` (caution/marginal), **Alert Red** `#c4535d` (destructive/error), **Stone** `#eeeae1` (neutral/disabled bg).

- Type scale (from the reference's own "Type scale (app)" panel): Nav title Manrope 800 / 20–26px, Section header Manrope 700 / 17–18px, Body Inter 500 / 15px, Caption/label Inter 600 / 12px.

## 2026-08-04 — getPriceForStoreAtTime() removed: verdict, bar chart, ranking, and pricing table were running on fabricated data

Follow-up to the "Cheaper Alternatives" fix below, tackling the larger related issue flagged there: `getPriceForStoreAtTime()` -- used by the DealModal's headline Real Saver/Fair Deal/Dodgy Deal verdict, its cross-store bar chart, the cheapest-store ranking list, and the "See pricing details" min/max/avg table.

- **How bad it actually was:** the function's `'30d ago'`/`'60d ago'`/`'90d ago'` snapshot lookups matched against hardcoded mock fixture date strings (`'Jun 10'`, `'May 15'`, `'May 01'`, etc.) that real `price_history.scraped_at` values can never produce. For every real live product, all three snapshot lookups silently fell through to a fabricated `standardPrice * storeMultiplier` guess -- meaning the average this whole screen compared "today's price" against was **always invented** for live data, never real. Worse: the app already computes a correct, real verdict for every deal at load time (`classifySpecial()`, stored as `deal.dealType`) -- this screen was silently recomputing a **second, independent, fake verdict** from the guessed average and showing that instead, so the headline judgment on a real deal could contradict the correct one already shown on the card one screen back.
- **It got theatrical in the Dodgy Deal explanation specifically:** the "why is this dodgy" paragraph branched on `product.id === 'avalanche-sachets-10pk'` (one specific mock product) for a hardcoded canned sentence, `product.id.length % 2 === 0` for a second canned sentence (meaningless for live data -- every real product id is a 36-character UUID, so this was true 100% of the time in practice), and otherwise fudged the displayed average by $1 whenever the real numbers didn't support a "higher than average" story. All three branches removed.
- **Fix:** deleted `getPriceForStoreAtTime()` entirely. Replaced with two small real-data-only helpers: `getRealPriceToday(store)` (today's real `currentDeals` price, or `null`) and `getRealAveragePrice(store)` (that same entry's `originalPrice` -- already either `classifySpecial()`'s real day-windowed normal price for an active special, or the flat real regular price otherwise; not a rolling average, not a guess). `barChartData` and `rankingList` now skip any store with no real data instead of inventing a bar or ranking entry. The headline verdict now reuses `deal.dealType` via the existing `HISTORY_DEAL_TYPE` mapping (already used correctly elsewhere for the same vocabulary translation, e.g. "All Checks" history) instead of recomputing a second verdict. `getPricingStatsForStore()` (the "See pricing details" table) now derives min/max/avg from real `priceHistory` rows for that store, falling back to today's real `currentDeals` price only when history is completely empty for that store (avoids double-counting today when history already includes it). Chart heading/copy changed from claims of "90 Day" / "last 90 days" (never true for this calculation) to "recent normal price" / "Current Price vs Recent Normal, By Store".
- **Peer review:** compiled `#app-source` clean after every edit. Built a full jsdom + pinned React 18.3.1 harness (lucide-react/motion/recharts stubbed inert, component identity cached per the established convention, network stubbed to fail so the app runs on `FALLBACK_PRODUCTS`) and drove it end-to-end: guest skip -> search "moccona" -> "Check Deals" on the cheapest result (Woolworths, mock `dealType: 'Real Deal'`) -> confirmed the modal opens, the verdict heading reads exactly "Real Saver" (correct `HISTORY_DEAL_TYPE` translation, not the old recompute), the bar chart's underlying data is `{Woolworths: current $9.50 / avg $11.50, New World: current $11.99 / avg $16.99}` -- matching the mock's own real `originalPrice` fields exactly, confirmed no stale `"last 90 days"` or `"90 Day Price History"` text remains and the new copy is present, and expanded "See pricing details" to confirm the table shows real min/max/avg computed only from actual `priceHistory` rows (New World $10.50/$16.99/$12.10, Woolworths $9.50/$10.50/$10.25 -- both hand-verified against the mock's own history arrays). ## 2026-08-04 — "Cheaper Alternatives" no longer fabricates a price for stores with no real data

User asked whether the app can suggest similar products for a specific special -- yes, `DealModal`'s "Cheaper Alternatives" section already did this (category match, cross-store, live since 2026-07-10). Checking how it holds up against the real live catalogue (vs. the mock data it was originally built against) surfaced a real bug.

- **Bug:** `getAnyProductPriceToday(p, store)` checked `p.currentDeals` for a real price first (fine), but if a category-mate had no real price row for a given store, it fell back to a hardcoded mock-era multiplier off `p.standardPrice` (Pak'nSave x0.95, New World x1.05, Four Square x1.08, FreshChoice x1.12) -- a guessed price rendered with zero visual distinction from a real one.
