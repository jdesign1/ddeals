## 2026-07-10 — Removed the gap above the docked sticky pills

Follow-up to the section-merge fix below: the pills stayed docked correctly now, but sat with a visible gap between the pinned search bar and the pill row once stuck.

- **Cause:** the results scroll container (`flex-1 overflow-y-auto px-4 py-5 space-y-6`) carried its own `py-5` top padding. `position: sticky`'s `top: 0` offset is measured from this container's own padding edge, so that padding wasn't just space before the first scroll -- it showed up as a permanent gap above the pill row for as long as it stayed stuck.
- **Fix:** dropped the container's top padding (`py-5` → `pb-5`, bottom-only). To avoid the "Results for '...'" heading landing flush against the search bar as a result, added `pt-5` directly to that heading `<section>` instead -- it scrolls away long before the pills would ever dock, so it can't reintroduce the same gap. The "Keep typing..." / popular-specials state didn't need any compensating change, it already carries its own `py-8` on its first inner `<div>`.
- **Peer review:** recompiled `#app-source` clean, grepped the compiled source to confirm the exact class changes landed (`px-4 pb-5 space-y-6` on the scroll container, `text-center space-y-2 pt-5` on the results heading). Re-ran all three existing jsdom harnesses from this thread (tap-to-open/scroll-reset/guest-state, clear-vs-close icon split, clear-as-text/merged-section/popular-specials) unchanged and clean -- this was a padding-only change so no new behavioural assertions were needed, just confirming nothing else regressed.

## 2026-07-10 — Fixed sticky pills (transform-vs-sticky bug), split clear/close search icons

Follow-up to the same day's "search opens on tap" work below, after the user reported the pill carousel still wasn't docking and asked for the search bar's X to just clear text (not close), the camera icon hidden in full-screen mode and replaced with a close-X there, and a proper clear option once text is typed.

- **Root cause of the sticky bug, found by inspection not guesswork:** the previous entry's fix wrapped the full-screen overlay in `<motion.div animate={{ opacity: 1, y: 0 }}>` for a slide+fade entrance. Framer Motion applies `y` as an inline `transform` style (e.g. `translateY(0px)`) and leaves it attached even once settled at `y: 0`. A `transform` on *any* ancestor of a `position: sticky` element becomes that element's containing block instead of its real scroll container, breaking the stick behaviour outright, in every browser -- not a rendering glitch, a direct consequence of the CSS spec (`transform`/`filter`/`perspective` all do this). Since the pill row lives inside that same overlay, it never had a chance to dock correctly once the entrance animation was added. Fixed by dropping `y` entirely and animating `opacity` only (`initial={{opacity:0}}` / `animate={{opacity:1}}` / `exit={{opacity:0}}`) -- opacity doesn't establish a containing block, so sticky works again, and the panel still fades in/out smoothly.
- **Inline field X now only clears text, doesn't close:** added `handleClearSearchText()` (clears `searchInputValue`/`activeSearchQuery` only) and pointed the field's existing `#clear-search-btn` at it instead of the old `handleClearSearch` (which also exited full-screen). Also removed the `React.useEffect` that auto-closed the full-screen view the instant `searchInputValue` went back to `''` -- that effect is what made "clear" and "close" inseparable no matter which button fired it (including backspacing the field out manually). Closing is now only ever explicit: the back arrow and the new close button below both still call `handleClearSearch` directly.
- **Camera icon hidden in full-screen mode, replaced with a close-X:** `renderSearchBar` takes a new `isFullScreen` param (both call sites already passed the same boolean as `autoFocus`, kept as a separate explicit param for clarity). The trailing icon slot now renders `#scan-barcode-btn` (Camera) only when `!isFullScreen`, and a new `#close-search-fullscreen-btn` (X icon, calls `handleClearSearch`) only when `isFullScreen` -- scanning a barcode isn't a thing you'd do mid-search, and the full-screen view now has an explicit close affordance in the bar itself in addition to the back arrow.
- **Peer review:** re-extracted `#app-source`, recompiled with the standard Babel config -- clean, confirmed no `y`/`x` remain on the search overlay's `motion.div` (grepped the source directly, not just trusting the diff). Ran the jsdom + pinned-React harness scripted end-to-end: home bar shows the scan button, no close-X; focusing the input opens full-screen with the scan button gone and the close-X present, no clear-X yet (empty field); typed "coffee" -- clear-X appears, sticky pill markup present, still full-screen; clicked the inline clear-X -- input emptied, **stayed** full-screen (shows "Keep typing..."), confirming it no longer closes; typed "milk" again, clicked the new close-X -- full-screen exited, back to the home bar with the scan button restored; re-opened via focus and confirmed the back arrow still closes it too (regression check). ## 2026-07-10 — Search bar: fixed mobile zoom-on-focus and suggestion lag

User reported the search bar zooms the whole page in when tapped on mobile, and that live suggested results lag noticeably while typing.

- **Zoom on activation:** the input used Tailwind's `text-sm` (14px); mobile WebKit (iOS Safari and friends) auto-zooms the viewport on focus of any input under 16px. Added a scoped `#search-input { font-size: 16px; }` rule — ID specificity overrides `.text-sm` without touching the input's other styling or disabling pinch-zoom app-wide via the viewport meta (left untouched).
- **Suggestion lag:** `SearchTab` had no memoization at all — the filter/store-match/sort pipeline over the full live catalogue (~12.7k products) re-ran synchronously on every render, including unrelated ones like the background pagination tick, and the sort comparator re-tokenised each product from scratch on every pairwise comparison instead of once per product. Wrapped the pipeline in `React.useMemo` keyed on a real `productsVersion` prop (the existing live-data tick from `App()`, now threaded down instead of left write-only), debounced the query driving that memo ~150ms behind the input's own instant value (the input and "Results for '...'" heading still update every keystroke), skipped the scan below the existing 3-character "Keep typing..." threshold, and precomputed relevance once per product before sorting instead of inside the comparator.
- **Peer review:** compiled `#app-source` with the project's standard Babel config, ran in Node + jsdom against a real parse of `Prototype/index.html` (so the CSS rule and viewport meta were checked against the actual file, not a stand-in), network stubbed to fail (confirms `FALLBACK_PRODUCTS` path). Confirmed the zoom rule is present and viewport doesn't disable user-scalable. Typed "coffee" character-by-character with no pause between keystrokes: the expensive scan ran 0 times mid-typing, exactly once after the debounce settled (was: once per keystroke, unthrottled, every time). Confirmed the settled results are correct — 4 real coffee products (Avalanche, Robert Harris, Nescafé, Moccona) with correct prices/stores. No thrown errors. Full details in `project.md`.

## 2026-07-10 — Search relevance ranking (category matches now outrank incidental keyword hits)

User reported not being able to find "butter" or "milk" via search. Category text was already part of the match (name/brand/category all searched), and the data itself is fine — real milk/butter products with correct categories and live prices are all in the DB, and load on page 0 of the streamed catalogue. The actual bug: no relevance ranking existed, so results fell back to cheapest-price-first, and a cheap chocolate bar ("Dairy Milk"), biscuit ("Milk Arrowroot"), or sauce ("Butter Chicken") that merely *mentions* the word buried the real category items a shopper was after.

- Added `getSearchRelevance()` — tokenises the query and product name/brand/category into whole words (so "milk" matches "Standard Milk" but not "Milky"/"Buttermilk-flavoured") and scores category match (4) > name match (3) > brand match (2) > the existing substring-only fallback (1).
- `sortedProducts` now sorts by this relevance score first; the user's chosen cheapest/discount/dodgy-rating sort is applied only as a tiebreaker within the same relevance tier, not as the primary order.
- Checked against live data: "milk"/"butter" now lead with genuine dairy-aisle items (coconut/almond/oat milk, Anchor/Westgold butter, butter-vs-margarine spreads — all actually co-categorised with dairy in the retailers' own taxonomy) ahead of incidental mentions. Some overlap between butter and spreads/margarine, or milk and "milk chocolate" labelling, is expected — that's real shared vocabulary in supermarket category taxonomies, not a bug.
- **Peer review:** compiled clean. jsdom + live-Supabase harness re-checked "coffee"/"weetbix" (still clean, on-target) plus "milk"/"butter" (79 and 68 real results, top-6 now genuinely category-relevant).
